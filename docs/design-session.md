# Docker 机制复现设计讨论

本文保留设计讨论中确认的要求。共享工具已进入实现，当前可执行接口、实现细化及外部部署前提以 [环境协议](environment-contract.md) 为准。

## 已确认

### 复现目标

每个 CVE 的必需目标是稳定、可重复的机制复现，允许直接调用内部函数、固定模型输出或预先建立必要状态。必须执行真实漏洞代码路径并验证实际效果；真实模型端到端复现不是必需条件。术语见 [CONTEXT.md](../CONTEXT.md)。

### 目标产品保真度

完整安装固定的上游目标版本及其依赖，允许直接调用内部函数，不要求每个案例都启动完整产品服务或经过正式外部入口。漏洞路径及相关防护逻辑使用该版本的上游实现，不以抽取、重写的最小漏洞程序代替目标产品。

这一选择兼顾验证对象的真实性与环境维护成本：触发流程可以简化，但验证结论必须对应固定的真实产品版本。

### 三场景自动验收

一次 Docker 复现必须自动运行并汇总三类场景：`vulnerable` 验证漏洞版产生预期无害效果，`patched` 验证修复版在服务正常时阻断相同输入，`benign` 验证正常任务在两版均可完成。缺少任一场景、服务未就绪或仅凭进程退出码成功，都不能判定环境通过。

### 默认实验隔离

Compose 默认使用内部网络且不发布端口，不挂载宿主机目录，不使用 `host` 网络或特权模式；容器丢弃全部 capabilities，启用 `no-new-privileges`，并设置 CPU、内存和进程数限制。证据写入实验结果目录或受控 Docker volume。确需网络、端口、额外权限或挂载的 CVE，必须在环境 README 中说明具体理由、目标和最小范围。

这一边界把漏洞影响限制在实验容器/VM 内，避免复现过程把真实宿主机资源暴露为攻击目标，同时保留对特殊漏洞的可审计例外。

### 复现脚本与验证器职责

`reproduce.py` 是机制层 PoC：在固定上游版本中执行触发步骤，可直接调用内部函数或使用固定输入，并记录可核查的事实证据。`verify.py` 是独立验证器：只读取结构化结果和受控证据，检查 `vulnerable`、`patched`、`benign` 三类条件，不再次触发漏洞，也不把 `reproduce.py` 的退出码当作漏洞证明。两者都随实验镜像进入容器，宿主机运行器只负责编排和收集结果。

## 架构决策

脚本职责和执行位置已确认，详见 [ADR-0003](adr/0003-reproduction-and-verifier-boundaries.md)。镜像来源和不可变标识已确认，详见 [ADR-0004](adr/0004-reproducible-immutable-images.md)。

大模型生成 PoC 的任务打包、候选执行和隐藏修复对照另行定义在 [ADR-0019](adr/0019-agent-generated-poc-evaluation.md)。统一 runner 已提供任务打包和候选编排，但每个环境仍需完成独立效果采集 Adapter；维护者机制 PoC 不得当作模型结果，Agent-PoC 结果也不改变当前机制验收状态。

## 已确认的镜像策略

每个环境提交可重建 Dockerfile 和构建上下文，分别构建漏洞版与修复版；源码固定完整 commit SHA，基础镜像固定 digest，最终镜像 digest 写入 `metadata.toml`。Compose 和复现记录只接受 `image@sha256:...`，不接受浮动 tag。

### 标准运行器入口

所有环境通过统一命令运行，例如 `python3 -m runner reproduce <product>/<CVE-ID>`。运行器负责检查或构建固定镜像、创建临时 Compose 项目、依次执行 `vulnerable`、`patched`、`benign`，调用验证器，收集日志和结构化证据并清理容器；可用 `--scenario`、`--timeout`、`--keep-on-failure` 等参数调试。`check` 和 CI 默认保持静态，不启动漏洞服务。

这一入口把生命周期和失败处理集中到共享工具，环境目录只实现 CVE 特定的触发与验证逻辑。

### 标准证据协议

采用统一 JSON 外壳与 CVE 专属事实。每个场景生成 `result.json`，记录环境 ID、场景、验证层、源码 commit、镜像 digest、时间、执行状态和证据引用。复现脚本记录事实，不输出漏洞是否成立的结论；验证器读取事实后生成 `verdict.json`，列出检查项、判定和原因。运行器汇总各场景判定，缺证据、超时或服务未就绪均不能判定通过。

证据须可通过容器内文件、哈希、结构化响应或受控日志复核，截图仅为辅助。哈希用于核对证据内容，不能单独证明漏洞效果。

### 退出码、重试与失败说明

运行器退出码约定为：`0` 表示所有要求的轮次和三类场景均通过；`1` 表示实验实际执行但至少一个场景或验证项失败；`2` 表示未运行（缺少 Docker、镜像 digest、修复版本或必要参数等）；`3` 表示运行器基础设施错误（Compose 调用异常或结果无法收集）。PoC、验证器和场景默认不自动重试；3 轮是明确的独立尝试，失败记录必须保留。

每个非通过结果必须额外记录失败阶段（build、pull、compose_up、healthcheck、reproduce、verify 或 cleanup）、分类状态、预期与实际、退出码（如有）、脱敏 stdout/stderr 引用、相关 evidence 引用、环境 ID、源码 commit、镜像 digest、平台和 run ID。缺少这些信息的 `failed` 不具备诊断价值。失败示例必须明确说明“漏洞断言失败”“修复阻断未证实”“服务未就绪”或“基础设施错误”，不能笼统标作修复成功或漏洞不存在。

### 就绪与草稿

`ready` 要求满足原有收录要求，并有证据证明漏洞版、上游修复版及两版正常任务全部验证通过。上游修复 commit 可以作为对照，不必等待正式发布版本。缺少上游修复的环境允许以 `draft` 收录并保留已有证据，不能标记为 `ready`。

这是对现有 `ready` 仅代表元数据完整的语义收紧。后续实现须同步更新 `CONTRIBUTING.md`、环境规范、runner 校验及相关测试；当前代码尚未执行此门槛。

### 无害效果边界

漏洞触发只能产生容器内、可验证、无害且可逆的效果，例如唯一 canary 文件、模拟数据库记录、受控响应标记或本地假数据接收。禁止读取真实凭据、访问宿主机目录或向外部目标发送数据。破坏性 CVE 使用隔离 fixture 和可逆替代效果，并在 README 说明替代效果与真实影响的对应关系。

该边界是安全约束，也是验收约束：没有可复核的安全效果，就不能用危险载荷补足证据。

### 固定输入与 fixture

每个环境必须把攻击输入、正常输入、模拟数据以及需要的固定模型输出纳入 `fixtures/`，并记录每项内容的 SHA-256。随机种子和相关环境变量显式固定；复现过程不能临时从网络获取未锁定的攻击材料。需要外部服务时使用容器内的确定性模拟服务。

### 漏洞版与修复版构建组织

默认由同一个环境 `Dockerfile` 和构建上下文构建漏洞版、修复版，通过明确的 variant 参数选择各自源码 URL、commit 和归档哈希；通用系统依赖和实验脚本保持一致。两个版本确实无法共用配方时，允许拆分 Dockerfile，但必须在 README 说明差异并证明实验依赖仍可比。

### 稳定性验收

晋升 `ready` 前，同一组固定镜像必须连续通过 3 轮完整三场景验收。每轮、每个测试使用全新容器及实验数据，避免残留文件或数据库状态影响结论；保留所有失败记录，不能只保存成功轮次。日常调试默认运行 1 轮。

### 首版验收平台

首版以 Linux amd64 原生 Docker 环境为必需验收平台。ARM64、Docker Desktop 等平台组合分别记录验证结果，完成同样的 3 轮验收后才声明支持。`ready` 仅表示在明确记录的平台上通过，不代表所有 Docker 平台均可复现。

### 正式镜像分发

正式实验镜像使用 GitHub Container Registry（GHCR）托管。维护者构建并推送漏洞版、修复版，取得仓库摘要并固定引用，再对这些镜像完成 3 轮验收；使用者按摘要拉取已验证镜像。Git 仓库保留 Dockerfile、构建上下文、PoC、验证器及说明文档。

本地构建的 image ID 不等同于 `image@sha256:...` 中的仓库摘要。GHCR 承接正式构建产物，实验仍在使用者自己的 Docker 环境运行。本决策尚未涉及实际上传镜像或设置仓库访问权限。

源码仍是环境的事实来源，GHCR 不是源码的替代品。每个环境必须保留源码 URL、完整 commit、构建配方和依赖约束；运行器既可拉取已验证 digest，也必须提供从该固定源码重建漏洞版和修复版的路径，并校验构建来源一致。

### 源码与依赖可重建性

构建允许联网下载，但源码和依赖的每一项内容都必须固定并记录：源码 URL、完整 commit、源码归档 SHA-256、语言与系统依赖的锁定版本及校验哈希、基础镜像 digest。环境应支持本地缓存和 `--offline` 构建；首版不要求把所有上游源码和依赖完整提交到 Git 仓库。

### Compose 编排拓扑

每个环境以 `vulnerable` 或 `patched` 互斥 profile 提供目标变体；数据库、队列、本地接收器等依赖作为同一 Compose 项目的辅助服务。目标镜像包含目标产品、`reproduce.py`、`verify.py` 和 fixtures，允许直接导入内部模块。PoC 以一次性命令执行，验证器在独立的一次性进程/容器中运行。运行器为每轮创建唯一 Compose project 名和 volume，结束后销毁以隔离状态；需要正式 HTTP 等入口的 CVE 由 PoC 通过内部网络访问目标服务。

### 服务就绪与失败分类

长运行目标服务及其依赖必须声明 Docker `healthcheck`；运行器在限定时间内等待所有必需服务 healthy 后才执行 PoC。超时、启动崩溃、健康检查失败和 PoC/验证器失败分别写入结果状态，不能混写成修复阻断。一次性内部函数实验可以不声明 healthcheck，但必须有明确的启动成功条件和全局超时。

### 双层 CI

普通 Pull Request CI 只运行 `runner check`、仓库工具测试、TOML/YAML 静态解析和 Dockerfile 静态检查，不拉取镜像、不构建漏洞服务、不执行 PoC。实际 Docker 复现使用单独的手动或定时工作流，只在隔离 VM 上运行，使用无真实凭据的环境并保存三轮结果；外部贡献者的 Pull Request 不自动触发该工作流。

### 维护者晋升与自动降级

环境作者可以提交 `draft`，只有维护者审阅公告、源码来源、Dockerfile、PoC、验证器和三轮证据后才能标记 `ready`。漏洞版或修复版源码 commit、镜像/基础镜像 digest、Dockerfile、Compose、fixtures、`reproduce.py`、`verify.py`、验收规则或运行器版本发生变化时，环境自动回到 `draft` 并将验证状态重置为 `not_run`；仅修改说明文字不触发降级。

### 工具链可追溯性

每份 `result.json` 额外记录 runner commit/version、Docker Engine 版本、Compose 版本、宿主平台和实验镜像 digest。运行器或验证器的材料性变化会使既有 `ready` 证据失效，需重新完成三轮验收。

### 证据复核与保留

维护者晋升 `ready` 时至少审阅完整三轮报告；涉及额外网络、权限或挂载例外时增加第二位审阅者。仓库长期保留脱敏的 verdict 摘要、证据 manifest、源码和镜像 digest；完整 stdout/stderr、Compose 日志和原始结果作为 CI artifact 保存。发现错误或撤回时降级环境并追加原因，保留历史证据，不删除记录。

## 待决问题

共享理解已确认并获准实现。实现细化：本地源码构建使用独立 image ID，GHCR 使用仓库 digest；静态 check 不写文件，执行入口或 refresh 自动降级旧 ready；永久保存小型可复核证据以免 CI artifact 过期。工具链版本变更是否影响实验语义仍需维护者判断。
